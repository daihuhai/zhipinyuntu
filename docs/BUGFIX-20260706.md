## 问题 1：职位推荐匹配超时

**现象**：选择简历后点击"智能匹配"，按钮一直 loading，~30s 后恢复但结果区为空。

**根因**：
- 后端 `match_service.recommend_jobs_for_resume` 精排阶段 `fine_rerank` 对 Top-50 候选逐个调用豆包大模型 (`ark_client.chat_json`)，50 次 LLM 调用耗时远超 30s。
- 前端 `request.ts` 全局 `timeout: 30000` (30s)，请求被 axios 中止，浏览器报 `net::ERR_ABORTED`。
- `Recommend.vue` 的 `fetchRecommend` 无 try/catch，异常被 axios 拦截器吞掉，`list` 保持空数组。

**修复方案**：
1. 后端：`fine_rerank` 输入从 Top-50 降到 Top-10，LLM 调用从 50 次降到 10 次。
2. 前端：match API 单独设置 `timeout: 120000` (120s)。
3. 前端：`fetchRecommend` 增加 try/catch + ElMessage 错误提示。

4. 前端：新增 Applications.vue 投递记录页面 + 路由 + 菜单。
5. 前端：Dashboard 投递记录 KPI 接入真实数据。

## 问题 16：智能匹配速度优化 (28s → 0.09s)

**现象**：求职者"职位推荐"点击"智能匹配"后等待 28-39s 才返回结果。

**根因**：
- 精排阶段 `fine_rerank` 对 Top-50 候选逐个串行调用豆包 LLM，50 次调用耗时巨大。
- embedding 模型 404 后每次匹配都重复尝试调用，浪费时间。
- 精排结果未缓存，二次匹配重复调用 LLM。

**修复方案**：
1. 精排候选数从 50 降到 4 (`RERANK_TOP_N = 4`)。
2. 批量精排：4 个候符合并为 1 次 LLM 调用 (`build_batch_rerank_messages`)。
3. 精排结果缓存：查 `match_record` 近 2 小时记录，命中则复用 (`_rerank_with_cache`)。
4. embedding 降级标记：首次失败后 `_embedding_disabled = True`，跳过后续重试。
5. `max_tokens` 优化：精排 4096→1024，单次兜底 4096→256。
6. `selectinload` 预加载关联关系，消除 N+1 查询。

**效果**：首次匹配（缓存未命中）~3s，二次匹配（缓存命中）0.09s。

## 问题 17：职位广场加载优化 (2s → 0.02s)

**现象**：职位广场每次请求耗时 2.03s。

**根因**：Vite 代理 target `http://localhost:8001` 中 localhost 优先解析为 IPv6 (::1)，连接失败后回退 IPv4，每次新连接都经历超时。

**修复方案**：
1. `vite.config.ts` 代理 target 改为 `http://127.0.0.1:8001`。
2. `app/db/base.py` `echo=False` 关闭 SQL 日志。

**效果**：2s → 0.02s（100 倍提升）。

## 问题 18：embedding 模型 404 降级

**现象**：`doubao-embedding-text-240915`、`doubao-embedding-text-240715` 等模型全部返回 404。

**根因**：ARK API Key 未开通 embedding 模型访问权限。

## 问题 19：精排缓存时区不匹配

**现象**：精排缓存查询 `MatchRecord.created_at >= cache_threshold` 永远为 False，二次匹配仍 28s。

**根因**：SQLite `func.now()` 返回 UTC 时间，`datetime.now()` 返回本地时间（UTC+8），时差 8 小时导致缓存查询条件不成立。

**修复方案**：`datetime.now()` → `datetime.utcnow()` 对齐 SQLite 的 UTC 时间。

## 问题 20：精排 as_completed 超时异常未捕获

**现象**：精排并发调用 LLM 时偶发 500 错误，日志 `TimeoutError: 1 (of 6) futures unfinished`。

**根因**：`as_completed(futures, timeout=30)` 的 timeout 异常未被 try/catch 捕获，直接抛到上层导致 500。

**修复方案**：去掉 `as_completed` 的 timeout 参数，改用 `f.result(timeout=25)` 控制单次超时，并添加未完成 future 的兜底处理（使用粗排分数）。

## 问题 21：职位广场搜索只匹配 title

**现象**：职位广场搜索框输入公司名（如"字节跳动"）或城市名（如"北京"），搜索结果为空或不含目标职位。

**根因**：后端 `job_service.list_public` 的 keyword 过滤仅 `Job.title.contains(keyword)`，不搜索 `company` 和 `work_city` 字段。

**修复方案**：使用 SQLAlchemy `or_` 组合查询，同时匹配 `title` / `company` / `work_city` 三个字段：
```python
from sqlalchemy import or_
stmt = stmt.where(or_(
    Job.title.contains(keyword),
    Job.company.contains(keyword),
    Job.work_city.contains(keyword),
))
```

## 问题 22：职位广场搜索未重置分页

**现象**：用户浏览到第 2 页后，在搜索框输入关键词搜索，结果区为空（因为搜索结果不足 2 页，但请求仍发送 `page=2`）。

**根因**：前端 `Jobs.vue` 搜索时直接调用 `fetchList()`，未将 `page` 重置为 1。

**修复方案**：新增 `handleSearch` 函数，点击搜索或回车时先 `page.value = 1` 再 `fetchList()`，同时搜索词 `.trim()` 去空格。

## 问题 23：登录/注册表单视线不集中

**现象**：登录页左侧品牌区占 55% 宽度，包含 logo + 标题 + 标语 + 4 条特性 + 3 项统计数据，内容过多分散用户注意力；右侧表单区仅占 45%，视觉权重不足。

**根因**：品牌区内容堆砌，与表单区形成"信息竞争"，用户视线在左右两侧来回跳动。

**修复方案**：

## 问题 30：职位推荐切页返回后结果丢失

**现象**：在"职位推荐"页选择简历并完成智能匹配后，点击某职位进入详情页，再点"返回"回到推荐页，发现简历选择器被清空、推荐列表消失，必须重新选择简历并再次等待匹配（耗时数十秒）。

**根因**：`Recommend.vue` 的 `resumeId` 和 `list`（推荐结果）存在组件 `ref` 中，组件卸载（路由跳转到详情页）后数据销毁，返回时组件重新挂载，状态归零。

**修复方案**：使用 `sessionStorage` 持久化推荐状态，实现切页返回后无缝恢复：
1. 新增 `CACHE_KEY = 'recommend_state_cache'`，缓存结构 `{ resumeId, list, timestamp }`。
2. `saveCache()` 在 `fetchRecommend` 成功和 `submitApply` 后调用，写入 sessionStorage。
3. `restoreCache()` 在 `fetchResumes` 中调用，优先级：路由 query `resume_id` > sessionStorage 恢复 > 空。
4. **30 分钟 TTL**：`Date.now() - state.timestamp > 30 * 60 * 1000` 时自动失效清除，避免过期数据误导。
5. session 关闭标签自动清理，不影响其他用户。
