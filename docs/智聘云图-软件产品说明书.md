## 1. 产品概述

### 1.1 产品定位

智聘云图是一款基于**文档智能解析**的人岗匹配平台，采用 B/S（Browser/Server）架构，面向求职者、企业招聘方、平台管理员三类用户群体。平台通过**大语言模型（LLM）** 自动解析简历与职位描述文档，构建个人与企业的**能力知识图谱**，并运用**六维度匹配引擎**实现精准的人岗双向推荐，从根本上提升招聘与求职的效率和匹配质量。

### 1.2 核心价值

| 价值维度 | 说明 |
|---------|------|
| 智能解析 | 基于豆包大模型（doubao-seed-2-1-pro）自动从 PDF/DOCX 文档中提取结构化信息，无需人工录入 |
| 精准匹配 | 六维度加权评分（技能 40% + 经验 20% + 学历 15% + 城市 10% + 薪资 10% + 项目 5%）+ LLM 语义精排 |
| 知识图谱 | 基于图数据库构建个人能力图谱、职位能力图谱和技能关联图谱，可视化展示能力结构 |
| 双向推荐 | 求职者端智能推荐职位，企业端智能推荐候选人，匹配理由由 AI 自动生成 |
| 实时通信 | WebSocket 实时推送消息，支持面试邀请、投递状态变更等即时通知 |

### 1.3 适用场景

| 场景 | 说明 |
|------|------|
| 高校毕业生求职 | 批量上传简历，AI 自动解析生成结构化简历，系统智能推荐匹配职位 |
| 企业批量招聘 | 发布职位 JD，AI 解析技能要求，系统自动推荐合适的候选人 |
| 人才市场/猎头服务 | 作为中台系统支撑大规模人岗匹配业务 |
| 企业内部人才盘点 | 通过知识图谱可视化展示员工能力结构，辅助人才决策 |

### 1.4 目标用户群体

| 用户角色 | 角色标识 | 主要诉求 |
|---------|---------|---------|
| 求职者 | ROLE_SEEKER | 上传简历、浏览职位、获取推荐、管理投递、查看能力图谱 |
| 企业招聘方 | ROLE_EMPLOYER | 发布职位、管理职位、查看候选人推荐、管理投递流程 |
| 平台管理员 | ROLE_ADMIN | 数据监控、用户管理、内容审核、系统配置、日志审计 |

## 4. 安装与部署

### 4.1 前端部署步骤

#### 开发环境

```bash
# 进入前端目录
cd frontend

# 安装依赖
npm install

# 启动开发服务器（默认端口 5173）
npm run dev
```

#### 生产构建

```bash
# 构建生产版本
npm run build

# 构建产物位于 dist/ 目录
# 将 dist/ 目录部署到 Nginx 静态文件目录
```

#### Nginx 配置示例

```nginx
server {
    listen 80;
    server_name your-domain.com;
    root /var/www/zhipin/dist;
    index index.html;

    # 前端静态资源
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 后端 API 反向代理
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 上传文件访问
    location /uploads/ {
        proxy_pass http://127.0.0.1:8000;
    }

    # WebSocket 代理
    location /ws/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

### 4.2 后端部署步骤

#### 开发环境

```bash

cd backend

# 创建虚拟环境

docker-compose logs -f backend

docker-compose up -d --build
```

### 4.3 数据库初始化

#### GreatSQL/MySQL 数据库初始化

```sql
-- 创建数据库
CREATE DATABASE IF NOT EXISTS zhipin CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 创建用户并授权
CREATE USER IF NOT EXISTS 'zhipin'@'%' IDENTIFIED BY 'your-password';
GRANT ALL PRIVILEGES ON zhipin.* TO 'zhipin'@'%';
FLUSH PRIVILEGES;
```

#### Neo4j 图数据库初始化

```sql
-- 创建空间（Neo4j 不需要，此为 NebulaGraph 语法示例）
CREATE SPACE IF NOT EXISTS zhipin(partition_num=1, replica_factor=1, vid_type=FIXED_STRING(64));
```

应用启动时，后端会自动执行 `Base.metadata.create_all()` 创建所有数据表，并自动创建默认管理员账号。

## 5. 快速入门指南

### 5.1 注册与登录（三种角色）

#### 求职者注册

1. 访问系统首页，点击"注册"按钮。
2. 选择"我是求职者"角色。
3. 填写用户名、手机号、密码等信息，点击"注册"完成。
4. 注册成功后自动登录，跳转到求职者工作台。

#### 企业注册

1. 访问系统首页，点击"注册"按钮。
2. 选择"我是企业"角色。
3. 填写企业名称、统一社会信用代码、联系人信息、用户名密码等。
4. 注册成功后自动登录，跳转到企业工作台。

#### 管理员登录

管理员账号由系统初始化时自动创建（默认用户名 `admin`），首次启动时后端日志会输出随机生成的密码。管理员通过登录页面使用账号密码登录。

### 5.2 简历上传与解析

1. 求职者登录后，进入"我的简历" → "上传简历"。
2. 点击上传区域，选择 PDF 或 DOCX 格式的简历文件（文件大小不超过 10MB）。
3. 系统自动上传文件并调用豆包大模型进行解析。
4. 解析过程约 5-15 秒，解析完成后页面自动刷新。
5. 解析成功后可查看结构化的简历信息，包括：姓名、学历、工作经历、技能清单等。
6. 如有需要，可点击"编辑"按钮手动修改解析结果。

### 5.3 职位发布流程

1. 企业用户登录后，进入"发布职位"页面。
2. 支持两种方式：
   - **手动填写**：逐项输入职位名称、薪资范围、工作城市、学历要求、经验要求、职位描述、技能要求等。
   - **AI 解析 JD**：粘贴职位描述文本，点击"AI 解析"，系统自动提取结构化信息并填充表单。
3. 确认信息无误后点击"发布"，职位状态为"招聘中"。
4. 发布成功后，可在"职位列表"中查看和管理已发布的职位。

### 5.4 智能匹配与推荐使用

#### 求职者端

1. 上传并解析简历后，进入"职位推荐"页面。
2. 系统自动基于简历内容进行六维度匹配计算，展示匹配度最高的职位列表。
3. 每个职位卡片展示匹配度百分比、各维度评分、AI 生成的匹配理由。
4. 点击感兴趣的职位可查看详情，点击"投递"按钮进行投递。

#### 企业端

## 9. AI 智能功能

### 9.1 简历智能解析

基于豆包大模型（doubao-seed-2-1-pro）的简历解析功能：

- **输入**：简历文档提取的纯文本（最多 8000 字符）
- **输出**：结构化 JSON 数据（含 20+ 个字段）
- **模型**：doubao-seed-2-1-pro（通过火山引擎 ARK API 调用）
- **温度参数**：0.0（严格结构化，不创意发挥）
- **最大输出 Token**：2048

解析字段包括：

| 字段 | 类型 | 说明 |
|------|------|------|
| name | string | 姓名 |
| gender | string | 性别 |
| age | int | 年龄 |
| phone | string | 手机号 |
| email | string | 邮箱 |
| current_city | string | 当前居住城市 |
| intention_cities | array | 意向城市列表 |
| education | string | 最高学历 |
| school | string | 毕业院校 |
| major | string | 专业 |
| work_years | int | 工作年限 |
| expected_salary_min | int | 期望薪资下限（K） |
| expected_salary_max | int | 期望薪资上限（K） |
| self_evaluation | string | 自我评价 |
| skills | array | 技能列表（名称 + 等级） |
| work_experience | array | 工作经历 |
| projects | array | 项目经验 |

### 9.2 JD 智能解析

基于豆包大模型的职位描述解析功能：

- **输入**：职位描述文本（最多 4000 字符）
- **输出**：结构化 JSON 数据（含 14+ 个字段）
- **模型**：doubao-seed-2-1-pro
- **温度参数**：0.0
- **最大输出 Token**：1024

解析字段包括：title、company、department、job_type、salary_min、salary_max、work_city、experience_required、education_required、headcount、description、requirements（技能要求列表）。

### 9.3 AI 智能分析

#### 简历完整度评分

基于豆包大模型对简历进行缺失分析，从以下维度评估：

| 分析维度 | 权重 | 说明 |
|---------|------|------|
| 基本信息 | 高 | 姓名、联系方式、所在城市是否完整 |
| 教育背景 | 中 | 学历、学校、专业是否填写 |
| 技能清单 | 高 | 技能是否足够，是否有热门技能缺失 |
| 工作经历 | 高 | 是否有工作经验描述 |
| 项目经历 | 中 | 是否有项目经验描述 |
| 自我评价 | 中 | 是否有自我评价，是否足够有吸引力 |
| 期望薪资 | 低 | 是否设定了合理的薪资范围 |
| 求职意向 | 低 | 意向城市是否明确 |

输出内容包括：
- overall_score：总体完整度评分（0-100）
- summary：一句话总体评价
- gaps：缺失项列表（含类别、标题、描述、优先级、建议值）

#### 改进建议

AI 针对每一项缺失给出具体可操作的改进建议，按优先级排序（high/medium/low）。

### 9.4 AI 智能匹配

匹配重排阶段，豆包大模型对候选对进行语义精排：

- **输入**：简历摘要 + 职位信息
- **输出**：score（0-100 整数）+ reason（自然语言匹配理由）
- **模型**：doubao-seed-2-1-pro
- **温度参数**：0.1（低温度，保证一致性）

#### 批量精排优化

支持一次 LLM 调用评估多个候选职位（当前最多 6 个），大幅降低 API 调用次数和延迟：

- 批量精排一次调用评估所有候选
- 批量失败时降级为并发单次精排（ThreadPoolExecutor，最多 8 并发）
- 单个候选超时 25 秒，避免无限等待

### 9.5 批量重排优化

系统实现了多级缓存加速机制：

| 缓存层级 | 缓存内容 | TTL |
|---------|---------|-----|
| 匹配记录缓存 | 2 小时内的匹配记录（match_record 表） | 2 小时 |
| Redis 缓存 | 热门数据查询结果 | 可配置（默认 300 秒） |
| Embedding 缓存 | 简历/职位向量（存储于数据库） | 持久化 |

### 9.6 缓存加速机制

- Redis 缓存服务自带降级保护，Redis 不可用时自动降级不影响业务
- 支持 JSON 序列化对象的缓存
- 支持 TTL 过期
- 支持批量删除（按前缀模式）
- 支持 `get_or_set` 模式（缓存不存在时自动调用 factory 获取并缓存）

## 10. 六维度匹配引擎

### 10.1 维度权重说明

匹配引擎采用六维度加权评分模型，各维度权重如下：

| 维度 | 权重 | 说明 |
|------|------|------|
| 技能匹配 | 35% | 候选人技能与职位技能要求的匹配程度 |
| 经验匹配 | 20% | 候选人工作年限与职位要求经验的匹配程度 |
| 学历匹配 | 10% | 候选人学历水平与职位学历要求的匹配程度 |
| 城市匹配 | 10% | 候选人当前/意向城市与职位工作城市的匹配程度 |
| 薪资匹配 | 10% | 候选人期望薪资与职位薪资范围的匹配程度 |
| 项目匹配 | 15% | 候选人项目经验丰富度 |

> **注意**：实际权重配置已在代码中调整为：技能 35% + 经验 20% + 学历 10% + 城市 10% + 薪资 10% + 项目 15%，总和为 100%。原始方案中技能 40% 的权重已在代码优化中调整。

### 10.2 各维度计算方式

#### 技能匹配度

```
技能匹配度 = Σ(命中技能权重 × 技能等级系数) / Σ(所有技能要求权重)

- 必须技能命中权重 = 1.0，优先技能命中权重 = 0.7
- 技能等级系数：精通=1.0, 熟练=0.8, 掌握=0.6, 熟悉=0.5, 了解=0.4
- 支持模糊匹配（包含关系）和别名归一化
```

#### 经验匹配度

```
经验匹配度 = 候选人工作年限与职位要求年限的匹配程度

- 应届要求：年限 ≤ 1 年 → 1.0，否则 → 0.7
- 范围要求（如"3-5年"）：在范围内 → 1.0，超出上限 → 线性递减至 0.5，低于下限 → 线性递增
- 无明确要求 → min(年限/5, 1.0)
```

#### 学历匹配度

```
学历匹配度 = 候选人学历等级与职位学历要求的匹配程度

- 学历等级：博士=5, 硕士=4, 本科=3, 大专/专科=2, 高中=1, 其他=0
- 候选人等级 ≥ 要求等级 → 1.0，否则 → 候选人等级/要求等级
```

#### 城市匹配度

```
城市匹配度 = 候选人与职位所在地的匹配程度

- 当前城市与工作城市匹配 → 1.0
- 意向城市列表包含工作城市 → 1.0
- 不匹配 → 0.3
```

#### 薪资匹配度

```
薪资匹配度 = 期望薪资区间与职位薪资区间的重叠度

- 重叠度 = 重叠区间长度 / 并集区间长度
- 无重叠 → 0.0
- 完全重叠 → 1.0
```

#### 项目匹配度

```
项目匹配度 = min(项目数量 / 3, 1.0)

- 项目数量从简历 raw_parse_json 的 projects 字段获取
- 最多 3 个项目即可达到满分
```

### 10.3 技能别名归一化

## 11. 知识图谱功能

### 11.1 图谱架构设计

| 节点类型 | 标识 | 属性 |
|---------|------|------|
| Person | 求职者 | name, role, education, work_years, city |
| Job | 职位 | title, company, city, salary_min, salary_max |
| Skill | 技能 | name, category |

| 边类型 | 源节点 → 目标节点 | 属性 |
|--------|-----------------|------|
| HAS_SKILL | Person → Skill | level, weight |
| REQUIRES | Job → Skill | level, req_type, weight |
| MATCHED | Person → Job | score |

### 11.2 个人能力图谱

求职者上传简历并解析成功后，系统自动构建个人能力图谱：

- 中心节点：Person（求职者）
- 一级节点：技能分类（Category，如"编程语言"、"框架"、"数据库"）
- 二级节点：Skill（具体技能名称 + 掌握等级）
- 边：HAS_CATEGORY（Person → Category）、INCLUDES（Category → Skill）

### 11.3 职位能力图谱

企业发布职位后，系统自动构建职位能力图谱：

- 中心节点：Job（职位）
- 叶节点：Skill（技能要求，区分"必须"和"优先"）
- 边：REQUIRES（Job → Skill），属性包含 req_type 和 weight

### 11.4 技能关联图谱

点击技能节点可查看该技能在所有人和职位中的关联情况：

- 查询与该技能相关的所有 Person 和 Job 节点
- 展示技能在人才市场和职位需求中的分布

### 11.5 可视化交互操作

| 操作 | 说明 |

## 12. 安全与权限

### 12.1 RBAC 权限模型

系统采用基于角色的访问控制（RBAC）模型，定义三种角色：

| 角色 | 标识 | 权限范围 |
|------|------|---------|
| 求职者 | ROLE_SEEKER | 简历管理、职位浏览、投递、收藏、消息、个人设置 |
| 企业 | ROLE_EMPLOYER | 职位管理、候选人查看、投递管理、消息、企业设置 |
| 管理员 | ROLE_ADMIN | 用户管理、简历管理、职位管理、日志查看、系统配置 |

前端路由守卫根据角色自动跳转到对应工作台，后端 API 通过依赖注入（`require_role`）校验角色权限。

### 12.2 JWT 认证机制

采用双 Token 机制：

| Token 类型 | 有效期 | 用途 |
|-----------|--------|------|
| Access Token | 2 小时 | API 请求认证（Bearer Token） |
| Refresh Token | 7 天 | 刷新 Access Token |

认证流程：

```
登录 → 获取 access_token + refresh_token
  ↓
API 请求携带 access_token（Authorization: Bearer xxx）
  ↓
access_token 过期 → 使用 refresh_token 获取新的 access_token
  ↓
refresh_token 过期 → 重新登录
```

Token 载荷包含：sub（用户 ID）、type（token 类型）、role（用户角色）、iat（签发时间）、exp（过期时间）。

### 12.3 数据隔离策略

| 数据 | 隔离策略 |
|------|---------|
| 简历 | 求职者仅能查看/编辑/删除自己的简历 |
| 职位 | 企业仅能查看/编辑/删除自己发布的职位 |
| 投递 | 求职者查看自己的投递记录，企业查看自己职位的投递 |
| 消息 | 用户仅能看到与自己相关的消息 |

### 12.4 接口安全

#### 速率限制（Rate Limiting）

基于 slowapi 实现，按 IP 地址限制请求频率：

| 接口 | 限制策略 |
|------|---------|
| 登录接口 | 限制频率，防止暴力破解 |
| 注册接口 | 限制频率，防止恶意注册 |
| 匹配接口 | 限制频率，防止滥用 |
| 上传接口 | 限制频率，防止磁盘耗尽 |

#### CORS 配置

- 仅允许配置的白名单来源访问
- 仅允许必要的 HTTP 方法（GET、POST、PUT、DELETE、PATCH）
- 仅允许必要的请求头（Authorization、Content-Type、X-Trace-Id）

#### 文件校验

| 校验项 | 规则 |
|--------|------|
| 文件扩展名 | 仅允许 .doc、.docx、.pdf |
| 文件大小 | 不超过 10MB |
| Magic Number | 校验文件头二进制签名，防止伪造扩展名 |

### 12.5 密码安全策略

- 密码使用 BCrypt 算法哈希存储（成本因子 12）
- BCrypt 限制密码最长 72 字节
- 生产环境 SECRET_KEY 强制更换，不可使用默认值
- 密码错误不提示具体原因（仅"账号不存在"或"密码错误"）

## 13. 性能优化

### 13.1 后端优化

#### Redis 缓存

| 缓存内容 | 缓存策略 | TTL |
|---------|---------|-----|
| 匹配记录 | 旁路缓存，先查缓存再查 DB | 2 小时 |
| 热门职位列表 | 按需缓存 | 300 秒 |
| 用户信息 | 按需缓存 | 300 秒 |
| 统计数据 | 按需缓存 | 300 秒 |

#### N+1 查询消除

使用 SQLAlchemy 的 `selectinload` 预加载关联数据：

```python
# 预加载技能和需求，避免 N+1 查询
resume = db.execute(
    select(Resume)
    .options(selectinload(Resume.skills))
    .where(Resume.id == resume_id)
).scalar_one_or_none()

jobs = db.execute(
    select(Job)
    .options(selectinload(Job.requirements))
    .where(Job.status == 1)
).scalars()
```

#### 批量精排

- 精排阶段：ThreadPoolExecutor 并发调用 LLM，10 候选从串行约 30 秒降到并发约 3 秒
- 批量精排：一次 LLM 调用评估最多 6 个候选，进一步降低延迟
- 超时控制：单次 LLM 调用超时 25 秒，避免无限等待

### 13.2 前端优化

#### 路由懒加载

所有页面组件均使用动态导入（`() => import(...)`），按需加载，减少首屏加载时间。

#### 骨架屏

列表加载时显示骨架屏组件（`SkeletonList.vue`），提升用户体验。

#### 请求去重

前端使用 `axios` 作为 HTTP 客户端，支持请求拦截和响应拦截，统一处理 Token 刷新和错误提示。

### 13.3 超时配置

| 组件 | 超时设置 | 说明 |
|------|---------|------|
| Redis 连接 | 2 秒 | socket 连接超时 |
| Redis 操作 | 2 秒 | socket 操作超时 |
| LLM 单次调用 | 25 秒 | 精排超时控制 |
| NebulaGraph 连接 | 5 秒 | 连接池超时 |
| 文件上传 | 根据文件大小 | 后端 10MB 限制 |
| 数据库连接池 | pool_recycle=3600 秒 | 连接回收 |

## 14. 常见问题与故障排除

### 14.1 简历解析失败

| 可能原因 | 解决方案 |
|---------|---------|
| 文件格式不支持 | 请上传 PDF 或 DOCX 格式文件 |
| 文件过大 | 文件大小不超过 10MB |
| 文件内容为空 | 检查文件内容是否完整 |
| 豆包 API 密钥无效 | 检查 ARK_API_KEY 配置是否正确 |
| 网络无法访问 ARK API | 检查服务器能否访问 `ark.cn-beijing.volces.com` |
| 简历文本超过 8000 字符限制 | 系统会自动截断，可尝试精简简历内容 |

### 14.2 图谱连线缺失

| 可能原因 | 解决方案 |
|---------|---------|
| NebulaGraph 未安装 | 系统自动降级为关系数据库模式，功能不受影响 |
| NebulaGraph 空间未创建 | 执行 `CREATE SPACE IF NOT EXISTS zhipin(...)` |
| NebulaGraph 连接配置错误 | 检查 NEBULA_HOST/NEBULA_PORT/NEBULA_USER/NEBULA_PASSWORD |
| nebula3-python 驱动未安装 | 执行 `pip install nebula3-python` |

### 14.3 匹配度不一致

| 可能原因 | 解决方案 |
|---------|---------|
| 简历或职位信息已变更 | 重新触发匹配计算 |
| 缓存未刷新 | 等待缓存过期（2 小时）或联系管理员清除缓存 |
| 技能别名未覆盖 | 联系管理员在代码中添加别名映射 |
| 豆包模型版本差异 | 检查 ARK_CHAT_MODEL 配置是否一致 |

### 14.4 上传超时

| 可能原因 | 解决方案 |
|---------|---------|
| 文件过大 | 压缩文件至 10MB 以下 |
| 网络不稳定 | 检查网络连接，尝试重新上传 |
| 服务器磁盘空间不足 | 联系运维清理磁盘空间 |
| Nginx 上传大小限制 | 检查 Nginx 配置的 `client_max_body_size` |

### 14.5 Neo4j 未安装

系统内置了完整的降级机制：

1. 图谱查询自动检测 NebulaGraph 连接状态。
2. 不可用时自动调用 `fallback` 方法，从关系数据库（GreatSQL/MySQL）查询数据。
3. 前端收到 `degraded: true` 标识后正常展示图谱。
4. 所有功能正常运行，仅图谱查询性能略低于图数据库模式。

### 14.6 Redis 不可用

Redis 缓存服务自带降级保护：

- Redis 连接失败时自动标记为 `available = false`。
- 所有缓存操作（get/set/delete）返回空值或 false，不抛出异常。
- 业务逻辑回退到直接查询数据库。
- 日志输出警告信息，不影响业务正常运行。

### 14.7 登录失败

| 错误提示 | 可能原因 | 解决方案 |
|---------|---------|---------|
| 账号不存在 | 用户名/手机号/邮箱未注册 | 检查账号信息是否正确，或注册新账号 |
| 密码错误 | 密码输入错误 | 检查密码，注意大小写 |
| 账号已被禁用 | 管理员已禁用该账号 | 联系管理员解禁 |
| 令牌无效或已过期 | Token 已过期 | 使用 Refresh Token 刷新或重新登录 |
